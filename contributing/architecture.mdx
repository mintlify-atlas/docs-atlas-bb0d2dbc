AntennaPod is built as a highly modularized Android application. Rather than one large `:app` module, functionality is split into focused Gradle modules organized by domain. Each module lives in a folder matching its Gradle path (for example, `:net:discovery` is in `./net/discovery/`) and contains a `README.md` describing its purpose.

## The service-interface / service split

Several functional areas use a deliberate two-module pattern to prevent circular dependencies:

- A **`service-interface`** module exposes an abstract interface (or a singleton holder). Consumer modules depend only on this thin interface module.
- A **`service`** module contains the concrete implementation and depends on everything it needs to do the actual work.
- The implementation is wired in at app startup, not at compile time.

Examples of this pattern in the codebase:

| Interface module | Implementation module |
|------------------|-----------------------|
| `:net:download:service-interface` | `:net:download:service` |
| `:net:sync:service-interface` | `:net:sync:service` |

### Startup wiring: `ClientConfigurator`

`PodcastApp.onCreate()` calls `ClientConfigurator.initialize(context)` once at app startup. `ClientConfigurator` performs two kinds of work:

1. **Initializes singletons** — database, preferences, network settings, SSL provider, notification channels.
2. **Registers implementations** — calls `setImpl()` / `setInstance()` on each service-interface holder, replacing the abstract placeholder with the real implementation.

```java
// From ClientConfigurator.java
DownloadServiceInterface.setImpl(new DownloadServiceInterfaceImpl());
FeedUpdateManager.setInstance(new FeedUpdateManagerImpl());
AutoDownloadManager.setInstance(new AutoDownloadManagerImpl());
SynchronizationQueue.setInstance(new SynchronizationQueueImpl(context));
```

This means any module that needs to trigger a download or sync only imports the lightweight `*-service-interface` module and calls the static interface — it never depends on the implementation module directly.

## EventBus for cross-component communication

AntennaPod uses [GreenRobot EventBus](https://github.com/greenrobot/EventBus) (v3.3.1) to communicate between components that would otherwise need direct references to each other.

All event classes live in the `:event` module. The EventBus index is generated at compile time using the `eventbus-annotation-processor` and registered in `PodcastApp.onCreate()`:

```java
EventBus.builder()
        .addIndex(new ApEventBusIndex())
        .logNoSubscriberMessages(false)
        .sendNoSubscriberEvent(false)
        .installDefaultEventBus();
```

The annotation processor makes subscriber lookup faster than runtime reflection. When you add a new event, define it in `:event` and annotate subscriber methods with `@Subscribe` in the consuming component.

## Data flow: feeds from network to screen

The following describes how a feed refresh moves data through the system:

<Steps>
  <Step title="Trigger">
    A feed refresh is triggered by calling `FeedUpdateManager.runOnce()` (or the periodic WorkManager task). `FeedUpdateManager` is resolved through the service-interface pattern — the caller does not depend on `:net:download:service`.
  </Step>
  <Step title="Download">
    `:net:download:service` schedules a `FeedUpdateWorker` via WorkManager. The worker fetches the raw XML over HTTP using the OkHttp client configured in `:net:common`, including SSL backports from `:net:ssl`.
  </Step>
  <Step title="Parse">
    The raw XML is passed to `:parser:feed`, which produces `Feed` and `FeedItem` model objects defined in `:model`.
  </Step>
  <Step title="Store">
    The parsed objects are written to the SQLite database managed by `:storage:database` (`PodDBAdapter`). Playback state, positions, and user preferences are stored separately in `:storage:preferences`.
  </Step>
  <Step title="Notify">
    After the database write, an EventBus event (from `:event`) is posted. UI components subscribed to that event update their views reactively without needing a direct reference to the database layer.
  </Step>
  <Step title="Display">
    UI modules such as `:ui:episodes` read from `:storage:database` and render the updated feed items using the shared components in `:ui:common` and images loaded by `:ui:glide`.
  </Step>
</Steps>
